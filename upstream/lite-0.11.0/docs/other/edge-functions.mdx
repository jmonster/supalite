import { Aside } from '@astrojs/starlight/components';

Run the Lite CLI under Bun to serve `supabase/functions/<name>/index.ts` through normal `dev` and `start`. Functions export a default object with a `fetch(request)` method and use Web APIs and ordinary package imports. Lite, SQLite, and native Bun workers share one process. Portable function source and the app's `supabase.functions.invoke()` calls can graduate unchanged to Supabase; dependency configuration, deployment, URL, and keys adapt to the destination.

<Aside type="caution">
Functions run trusted project code with the host's permissions; workers are not a permission sandbox. Bun's [Worker API is experimental](https://bun.com/docs/runtime/workers). Full Supabase runtime compatibility is not claimed.
</Aside>

## Run the CLI with Bun

Automatic Functions execution requires **Bun 1.4.2 or later**. Bun 1.4.2 is the qualified version. Follow [Bun's installation instructions](https://bun.com/docs/installation) and check `bun --version`. Invoke the CLI entrypoint explicitly with `bun`; a package runner may otherwise follow its Node shebang. The local Functions workflow does not need a Node executable, Deno, Docker, a separate Functions service, or a custom compiler/runtime binary.

Bun loads the TypeScript source directly and resolves packages from normal installed dependencies. Install dependencies before starting Lite. This path has no Lite-specific resolver, bundling step, or managed dependency cache.

## Run the portable SQLite example

The repository's `examples/functions-portable` contains a conventional `tasks` function, SDK client, PostgreSQL-format migration, and separate local and Supabase configurations. From the repository root:

```sh
bun install
cd examples/functions-portable
bun install
bun ../../upstream/lite-0.11.0/dist/cli/index.js dev \
  --config supabase/config.lite.toml --no-admin
```

`lite dev` applies the normal migration automatically. The example's `db.driver = "sqlite-postgres"` selects PostgreSQL-to-SQLite translation; Bun's existing SQLite adapter provides the connection. Data persists in `.lite/tasks.sqlite`.

In another terminal, from `examples/functions-portable`:

```sh
SUPABASE_URL=http://127.0.0.1:54321 \
SUPABASE_PUBLISHABLE_KEY=sb_publishable_portability_demo \
bun app/acceptance.mjs
```

The eight acceptance checks exercise create, read, update, read-after-update, independent Data API read, validation errors, function-owned `OPTIONS`, and production-style path/query routing. The demo disables gateway JWT verification and user sign-in and uses local placeholder keys. Add application authorization before exposing it.

## Source and dependency portability

Write a conventional Fetch handler, without a Lite-specific API:

```ts
export default {
  async fetch(request: Request): Promise<Response> {
    return Response.json({ method: request.method });
  },
};
```

Use bare package imports and relative imports for shared code. Pin the dependencies in the project's normal `package.json` and install them with `bun install`. The example imports `@supabase/supabase-js`, `@supabase/supabase-js/cors`, and `node:process`; its package dependency is exact:

```json
{
  "dependencies": {
    "@supabase/supabase-js": "2.117.2"
  }
}
```

For Supabase, the example's `supabase/functions/tasks/deno.json` maps both bare imports explicitly to that same version:

```json
{
  "imports": {
    "@supabase/supabase-js": "npm:@supabase/supabase-js@2.117.2",
    "@supabase/supabase-js/cors": "npm:@supabase/supabase-js@2.117.2/cors"
  }
}
```

This is deployment configuration; Bun does not use `deno.json`, `deno.jsonc`, or Deno import maps to resolve modules. Lite rejects a configured `functions.<name>.import_map` for local execution. Direct `npm:` / `jsr:` specifiers, `Deno.serve`, and other Deno APIs are not supported by this path. Existing functions that use those features need source changes before they fit the portable subset. Keep Bun-only APIs out of source intended for Supabase, and verify your dependencies on both runtimes.

The example's function source and eight-check SDK client have passed on Bun 1.4.2 and locally against official Supabase Edge Runtime 1.77.1. The function file was identical in both runs; only runtime and dependency configuration differed. This establishes that example's portability, not arbitrary-function compatibility, performance, or hosted deployment. Use Supabase's normal tooling with `supabase/config.toml`, the migration, function, and app files to deploy; supply that project's URL and keys. SQLite's documented SQL/API limitations still apply locally.

## Discovery, environment, and refresh

- `dev` / `start` discovers directories with `supabase/functions/<name>/index.ts`. `_shared` is importable source, not an endpoint. `enabled = false` excludes a function.
- Optional `[functions.<name>]` settings include `entrypoint` and `verify_jwt`. Entrypoint paths resolve relative to the selected config file. An explicitly configured missing entrypoint fails clearly.
- `[edge_runtime] enabled = false` disables automatic execution. `policy = "oneshot"` is the default; `"per_worker"` reuses workers. The configuration name is retained for Supabase compatibility.
- Custom secrets come from `supabase/functions/.env` through `process.env` (or Bun's `Bun.env`). Lite supplies local `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_PUBLISHABLE_KEYS`, `SUPABASE_SECRET_KEYS`, and `SUPABASE_FUNCTION_SLUG`. Env-file entries with the reserved `SUPABASE_` prefix are ignored, so copied production credentials do not redirect local SDK calls. Key maps contain a `default` entry when configured.
- Configured credentials take precedence. An existing `auth.jwt_secret` can supply local `anon` / `service_role` JWT fallbacks. These identify API roles, never a fabricated signed-in user. Keep secret and service-role keys in server code.
- `dev` refreshes the functions tree, including shared files and `.env`, configured entrypoints, and the project's `package.json` / `bun.lock`. TOML/JSON `functions` and `edge_runtime` settings also refresh. Install changed dependencies with Bun. Restart for executable configs, other server settings, imports outside the watched paths, or dependency files under `node_modules`. `start` does not watch.

Workers receive the supplied function environment instead of inheriting the host's environment. This prevents accidental env leakage through `process.env`; it does not restrict trusted code's filesystem, network, or subprocess access. Automatic worker setup belongs to Bun-hosted CLI `dev` / `start`; embedded `App` and Vite integrations can use the advanced executor below.

## Worker lifetime

The runner permits four workers in total and, with `per_worker`, eight active requests per worker. Requests beyond available capacity receive `503 BUSY` without an unbounded queue. Worker startup has a 60-second deadline. Each invocation has a 150-second deadline covering startup, execution, and response-body consumption. A timeout before response headers returns `504`; after headers, the response stream fails. A timed-out worker is retired; after a two-second shutdown grace period, native worker termination stops code that has not exited, including synchronous JavaScript that does not yield.

`oneshot` retires the worker after its response body completes or is cancelled. `per_worker` keeps globals available until 60 seconds of inactivity, a reload, failure, or CLI shutdown. Client cancellation drains the worker's active requests before retiring it; a timeout terminates the worker and can interrupt other active requests on that worker. Background work has no completion guarantee after its request ends.

## Requests, CORS, and verification

The app calls `/functions/v1/{name}`. The built-in bridge removes `/functions/v1` before forwarding the request to the worker, so `tasks/123?view=full` reaches the function as `/tasks/123?view=full`, matching [Supabase's function-name-prefixed routing](https://supabase.com/docs/guides/functions/routing). Methods, query strings, end-to-end headers, bodies, and response streams pass through; hop-by-hop headers and decompression metadata are normalized at the proxy boundary. `HEAD` suppresses the response body. Request abort and response-stream cancellation are forwarded over the local HTTP transport. Handler-level abort listeners and stream-cancel callbacks depend on Bun transport behavior and are not guaranteed; cleanup must be cooperative. Region hints do not select a real region.

All `OPTIONS` requests bypass gateway credential verification and reach the handler. The function owns its CORS headers and preflight response, as in [Supabase's CORS guide](https://supabase.com/docs/guides/functions/cors). Lite does not overwrite the handler's CORS policy.

`verify_jwt` defaults to `true`. Requests other than `OPTIONS` need a valid gateway credential:

- `Authorization: Bearer ...` is authoritative when present. Lite recognizes configured/custom-resolver API keys or verifies HS256 JWTs using `auth.jwt_secret`. Invalid authorization does not fall back to `apikey`.
- Without `Authorization`, `apikey` can identify a configured `auth.publishable_key` / `auth.secret_key` or a key recognized by `options.server.apiKeys.resolver`. A familiar key prefix alone grants no access.
- Recognized API keys do not fabricate JWT claims or a signed-in user. Secret keys are rejected for browser-like user agents. `options.server.apiKeys: false` disables key recognition, but does not disable `verify_jwt`.
- Valid legacy anon/service-role JWTs and user JWTs are accepted without a database user/session lookup. Asymmetric JWT signing keys and JWKS verification are not supported.

Gateway verification does not authorize application actions. A publishable key is public. Authorize the caller inside the function; pass the caller's authorization to the Supabase client when database operations should use that caller's RLS context. With `verify_jwt: false`, the gateway allows keyless requests. Validate webhook signatures or other application credentials before accepting sensitive operations.

## Advanced: injected executors

Embedded applications and custom runtime integrations can provide a trusted `options.drivers.functions.fetch(request, context)` executor. An explicit driver takes precedence over the CLI's automatic discovery and worker setup. This is an advanced integration point; the portable SDK example above uses ordinary function files.

Configure allowed names in `functions`; disabled/unconfigured functions and missing executors return 404. Unlike the built-in bridge, this executor receives the original `Request` with the full gateway URL, unread body, headers, and abort signal. `context.jwt` contains verified JWT claims or `null`; `apiKeyType` is `"publishable"`, `"secret"`, or `null`. Both are `null` for `OPTIONS` or `verify_jwt: false`. Return a Web `Response`; SDK decoding/error handling and streaming work normally. Add handler-owned CORS when browsers call it cross-origin.

Executors run trusted host code with the host's permissions. Direct database access can bypass Data API RLS.

## Limits and graduation

- Automatic source execution requires Bun-hosted `dev` / `start`. The portable Lite core remains usable in its other hosts; an embedded `App` or Vite plugin does not create workers automatically.
- No separate `functions serve` command, hosted Functions deployment/management API, or regional routing. Use Supabase's tooling for deployment.
- Deno APIs, Deno import-map resolution, direct `npm:` / `jsr:` specifiers, and Supabase-specific APIs such as `EdgeRuntime.waitUntil` are outside this runtime. WebSocket upgrades through the Functions gateway are not implemented.
- SQLite provides no PostgreSQL wire protocol. Functions using direct PostgreSQL sockets or requiring `SUPABASE_DB_URL` need a compatible PostgreSQL backend. Lite does not synthesize a SQLite-compatible `SUPABASE_DB_URL`.
- Runtime APIs, package compatibility, SQL `rpc()`, and database webhooks retain their own limitations. Local workers are not a safe multi-tenant execution boundary for untrusted code.

See [Compatibility](/compatibility), [Embedded usage](/integrations/embedded), and [Supabase Edge Functions](https://supabase.com/docs/guides/functions).
